# HTTP-методы

## Зачем нужны методы

HTTP-метод описывает намерение клиента относительно ресурса. Метод влияет на маршрутизацию, кеширование, повтор запросов, работу прокси и ожидания клиента.

```http
GET /articles/42 HTTP/1.1
Host: example.com
```

## Три важные характеристики

### Safe

Safe-метод предназначен только для чтения и не должен запрашивать изменение состояния сервера. Safe-методы: `GET`, `HEAD`, `OPTIONS`, `TRACE`.

Логирование и статистика могут изменяться, но клиент не просит изменить бизнес-ресурс.

### Idempotent

Повторение одинакового запроса один или несколько раз должно иметь тот же предполагаемый эффект, что и однократное выполнение.

Идемпотентны: `GET`, `HEAD`, `PUT`, `DELETE`, `OPTIONS`, `TRACE`.

Идемпотентность относится к эффекту, а не к идентичности ответа. Повторный `DELETE` может сначала вернуть `204`, а затем `404`, но ресурс всё равно удалён.

### Cacheable

Метод допускает кеширование ответа по правилам HTTP. Обычно кешируют `GET` и `HEAD`. Ответы на `POST` могут кешироваться при явной информации о свежести, но это поддерживается и используется значительно реже.

## Основные методы

| Метод | Назначение | Safe | Idempotent |
| --- | --- | --- | --- |
| `GET` | Получить представление ресурса | Да | Да |
| `HEAD` | Получить заголовки как у `GET`, без тела ответа | Да | Да |
| `POST` | Передать данные на обработку или создать подчинённый ресурс | Нет | Обычно нет |
| `PUT` | Создать или полностью заменить ресурс по известному URI | Нет | Да |
| `PATCH` | Частично изменить ресурс | Нет | Не гарантируется |
| `DELETE` | Удалить ресурс | Нет | Да |
| `OPTIONS` | Узнать доступные параметры коммуникации | Да | Да |
| `CONNECT` | Создать туннель через прокси | Нет | Нет |
| `TRACE` | Диагностический loopback запроса | Да | Да |

## `GET`

```http
GET /users/42 HTTP/1.1
```

- читает ресурс;
- параметры фильтрации обычно передаются в query string;
- тело `GET` не имеет общепринятой семантики и плохо поддерживается посредниками;
- хорошо сочетается с кешированием.

`GET` не должен использоваться для удаления или оплаты: браузер, crawler или prefetch может выполнить его без намерения пользователя изменить состояние.

## `HEAD`

Сервер возвращает те же заголовки, что и для `GET`, но без response body.

Применение:

- проверить существование ресурса;
- узнать `Content-Length`;
- проверить валидаторы кеша;
- получить метаданные без скачивания тела.

## `POST`

```http
POST /orders HTTP/1.1
Content-Type: application/json

{"productId":10,"quantity":2}
```

Применяется для создания ресурса с серверным назначением URI или запуска операции. Часто возвращает `201 Created` и `Location`.

Повтор запроса может создать два заказа. Для безопасных повторов применяют idempotency key:

```http
Idempotency-Key: 7eb0f23b-...
```

Сервер должен сохранить связь ключа с результатом операции.

## `PUT`

```http
PUT /users/42 HTTP/1.1
Content-Type: application/json

{"id":42,"name":"Alex","role":"admin"}
```

Обычно означает полную замену состояния ресурса по известному URI. Повтор одинакового `PUT` приводит ресурс к тому же целевому состоянию, поэтому метод идемпотентен.

## `PATCH`

```http
PATCH /users/42 HTTP/1.1
Content-Type: application/merge-patch+json

{"name":"Alexey"}
```

Применяет частичное изменение. Идемпотентность зависит от формата и операции:

- `set name = Alexey` может быть идемпотентной;
- `increment balance by 10` не идемпотентна.

## `DELETE`

```http
DELETE /users/42 HTTP/1.1
```

Метод идемпотентен по предполагаемому эффекту. После одного или нескольких успешных выполнений ресурс должен оставаться удалённым.

## `OPTIONS` и CORS preflight

Браузер может отправить preflight:

```http
OPTIONS /api/orders HTTP/1.1
Origin: https://frontend.example
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type
```

Сервер отвечает CORS-заголовками. Preflight проверяет разрешение браузеру отправить основной cross-origin запрос; это не механизм аутентификации.

## `CONNECT` и `TRACE`

`CONNECT` используется прокси для создания туннеля, например к HTTPS-серверу.

`TRACE` возвращает диагностическое представление запроса. Его часто отключают из соображений безопасности и отсутствия практической необходимости.

## `PUT` против `PATCH`

| `PUT` | `PATCH` |
| --- | --- |
| Обычно полная замена | Частичное изменение |
| Идемпотентен по семантике | Идемпотентность не гарантируется |
| Клиент отправляет целевое представление | Клиент отправляет инструкции или diff |

Конкретный API должен документировать точную семантику.

## Типичные вопросы

### Идемпотентность означает одинаковый HTTP-ответ?

Нет. Она означает одинаковый предполагаемый эффект на сервере.

### Может ли `POST` быть идемпотентным?

Метод не идемпотентен по стандартной семантике, но приложение может обеспечить идемпотентное поведение через idempotency key.

### Можно ли отправлять body в `GET`?

Физически некоторые клиенты это позволяют, но у тела `GET` нет общепринятой семантики; посредники и серверы могут его не поддержать. Для совместимого API используют query или другой метод.

### Почему `DELETE` идемпотентен, если второй ответ может быть `404`?

Потому что бизнес-эффект одинаков: ресурс отсутствует.

## Краткий ответ

> HTTP-метод задаёт намерение запроса. Safe-методы не запрашивают изменение состояния, а идемпотентные методы можно повторять без дополнительного предполагаемого эффекта. `GET` читает, `POST` передаёт данные на обработку, `PUT` полностью заменяет, `PATCH` частично изменяет, `DELETE` удаляет, а `OPTIONS` описывает возможности коммуникации и используется в CORS preflight.
